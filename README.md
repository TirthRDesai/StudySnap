# StudySnap

Upload a book (PDF) and get **flashcards**, a **quiz** and a plain-language **explainer** for it. Everything is generated by models running on your own machine through [Ollama](https://ollama.com), so there are no per-token costs and the book stays under your control.

See [PRD.md](PRD.md) for the product requirements, AI design and security model.

## What it does
- **Flashcards:** written chapter by chapter (over-generated), then the most important N across the whole book are kept. Pick *Exam prep* or *Overview* mode. The full ranked pool is stored, so the UI can show the top K without regenerating.
- **Quiz:** multiple-choice questions with explanations, scored in the browser, attempts saved.
- **Explainer:** book → chapter → section explanations at three depths (Simple, Student, Detailed), plus a glossary.

## Architecture
```
Browser (Next.js)
   │ sign in, upload PDF, read results            ┌────────────────────────┐
   ├────────────── Supabase (local) ──────────────┤ Auth · Postgres · RLS  │
   │                                              │ Storage: private books │
   │ POST /books/{id}/jobs  (Bearer token)        └───────────▲────────────┘
   ▼                                                          │ service role
FastAPI backend ── verifies the token with Supabase Auth ─────┘
   │ single-worker job queue
   ▼
Ollama (`ollama serve`): generation + embeddings
```
- The browser talks to Supabase directly for everything it owns (row-level security limits every table to the signed-in user, and the `books` bucket to `<user_id>/…`).
- The backend never trusts a user id from the request: it asks Supabase Auth who the token belongs to, then checks the book is theirs.
- Jobs run one at a time so the GPU isn't shared; progress is written to the `jobs` table and the UI polls it.

## Run it locally

**Prerequisites:** Docker Desktop (running), Node.js 20+, Python 3.10+, [Ollama](https://ollama.com/download).

### 1. Ollama
```bash
ollama serve
```
```bash
ollama pull qwen2.5:7b-instruct
```
```bash
ollama pull mxbai-embed-large
```
(`ollama serve` may already be running as a background app after installing Ollama.)

### 2. Local Supabase
From the repo root. The first start downloads several Docker images.
```bash
npx supabase start
```
This applies `supabase/migrations/` (tables, RLS policies and the private `books` bucket). Then print the keys you need:
```bash
npx supabase status -o env
```
Studio is at http://127.0.0.1:54323 and the test mailbox at http://127.0.0.1:54324. Email confirmation is off locally, so sign-ups work immediately.

### 3. Backend
```bash
cd Backend
python -m venv .venv
```
```bash
.venv\Scripts\pip install -r requirements.txt
```
Copy `Backend/.env.example` to `Backend/.env` and fill in `SUPABASE_ANON_KEY` (`ANON_KEY`) and `SUPABASE_SERVICE_ROLE_KEY` (`SERVICE_ROLE_KEY`). Then:
```bash
.venv\Scripts\python -m uvicorn app.main:app --port 8000 --reload
```
On macOS/Linux use `.venv/bin/…` instead of `.venv\Scripts\…`. Check http://127.0.0.1:8000/health.

### 4. Frontend
```bash
cd Frontend
npm install
```
Copy `Frontend/.env.example` to `Frontend/.env.local` and fill in `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Then:
```bash
npm run dev
```
Open http://localhost:3000, create an account, upload a PDF and generate.

## Using a hosted Supabase later
Nothing here is tied to the local stack. For a hosted project: create it in the Supabase dashboard, link and push the schema (`npx supabase link`, `npx supabase db push`), then put that project's URL and keys in the two env files. Keep the service-role key on the server only. Review the PRD's security section (9a) before exposing the backend publicly: in particular set `FRONTEND_ORIGIN` to your real site and keep Ollama bound to localhost.

## Limits (v1)
- Text PDFs only (no OCR for scanned books), up to 50 MB, no password-protected files.
- Output quality depends on the local model. Spot-check generated cards before relying on them.
- Chapter detection uses the PDF's bookmarks, then "Chapter N" headings, then fixed page ranges.
